# BigO Inspector

BigO Inspector — учебный MVP расширения для VS Code. Он проходит по C++ исходникам и заголовкам открытой папки, получает AST от Clang и показывает ориентировочную оценку Big O для определений функций, краткое объяснение и график типовых кривых роста.

> Это статическая эвристика для лабораторной работы. AST нужен, чтобы находить конструкции языка надёжнее, чем регулярными выражениями, но набор правил намеренно ограничен. Результат — подсказка, а не формальное доказательство сложности.

## Быстрый запуск

Требуются VS Code 1.85+, Node.js 18+ и установленный `clang++`, доступный в PATH.

1. Откройте папку `bigo-inspector` в VS Code.
2. Установите зависимости разработки: `npm install`.
3. Запустите `npm run build`, затем `npm test`.
4. Нажмите F5. Откроется Extension Development Host с примером из `sample/`.
5. В новом окне откройте командную палитру (`Ctrl+Shift+P`) и запустите **BigO Inspector: Analyze C++ Project**.

Если у проекта есть `compile_commands.json` в корне, расширение берёт параметры компиляции оттуда. Иначе использует `-std=c++17`. Путь к компилятору и стандарт настраиваются через `bigoInspector.clangPath` и `bigoInspector.standard` в настройках VS Code.

## Как проверить свой файл

После нажатия F5 откроется отдельное окно **Extension Development Host** с примером `sample.cpp`. Чтобы проверить свой код, в этом отдельном окне выберите **File → Open Folder…** и укажите папку своего C++ проекта (или папку, где лежит один нужный `.cpp` файл). Затем нажмите `Ctrl+Shift+P` и выберите **BigO Inspector: Analyze C++ Project**. Расширение просканирует `.cpp`, `.cc`, `.cxx` и заголовки `.h/.hpp` в открытой папке и покажет отчёт рядом с редактором. Отдельно вставлять или копировать код в расширение не нужно. Если компилятор не найдёт `clang++` или заголовки проекта, ошибки появятся внизу отчёта.

## Архитектура

```text
VS Code command
    └── src/extension.ts  находит .cc/.cpp/.cxx и заголовки по workspace
          ├── src/clang.ts  запускает clang++ -fsyntax-only -Xclang -ast-dump=json
          ├── src/analysis.ts  применяет простые правила к AST
          └── Webview  сводка, таблица функций, переход к строке, canvas-график
```

TypeScript компилируется обычным `tsc` в несколько CommonJS-модулей, поэтому отдельный сборщик и нативный модуль не нужны. AST декодируется стандартным `JSON.parse`. Один файл компилируется отдельно; ошибки одного файла показываются в отчёте и не останавливают остальные. Для проектов с нестандартными include-путями рекомендуется сгенерировать `compile_commands.json` (например, настройкой CMake `CMAKE_EXPORT_COMPILE_COMMANDS`).

## Правила оценки в MVP

| Найденная структура | Оценка |
| --- | --- |
| Нет циклов или самовызова | `O(1)` |
| Цикл с постоянной числовой границей, например `i < 10` | `O(1)` |
| Цикл со счётчиком, который меняется на постоянную величину к переменной границе | `O(n)` |
| Цикл со счётчиком, который умножается/делится на константу | `O(log n)` |
| Два вложенных линейных цикла | `O(n²)` |
| Три вложенных линейных цикла | `O(n³)` |
| Один линейный и один вложенный логарифмический цикл | `O(n log n)` |
| Два вложенных логарифмических цикла | `O(log² n)` |
| Последовательные циклы | Максимум из их оценок, а не произведение |
| Один рекурсивный вызов с аргументом `n - c` | `O(n)` |
| Один рекурсивный вызов с аргументом `n / c` | `O(log n)` |
| Два рекурсивных вызова с аргументом `n - c` | `O(2ⁿ)` |
| Два вызова с аргументом `n / 2` и линейная работа на шаге | `O(n log n)` |
| Цикл с непонятным условием или шагом | `O(?)` |
| Взаимная или нераспознанная рекурсия | `O(?)` |

Распознаются определения функций, методов и конструкторов. Для `for` анализатор сопоставляет объявленный счётчик с условием и шагом. Для `while` он ищет простые случаи изменения переменной из условия, включая деление пополам. Вложенные циклы объединяются по одной ветке вложенности, а последовательные циклы сравниваются по максимуму. Вызовы функций, определения которых есть в открытом проекте, учитываются транзитивно; вызов внутри цикла умножает сложность вызываемой функции на оценку цикла. Для рекурсии поддержаны простые прямые шаблоны с базовым условием и уменьшением аргумента на константу или делением на константу. Взаимная рекурсия и другие формы остаются `O(?)`. Анализ не моделирует стоимость библиотечных функций, независимые размеры входа, ранние выходы и все варианты изменения переменных. Для неподдерживаемого шаблона выводится неизвестная оценка, чтобы не выдавать догадку за точное значение.

## Проверки

`npm test` сначала собирает TypeScript, затем запускает встроенный Node.js test runner. Тесты проверяют постоянную, линейную и логарифмическую границы, вложенные и последовательные циклы, стоимость межфункциональных вызовов и несколько типов рекурсии, неизвестные случаи и фильтрацию функций из заголовков. Пример `sample/sample.cpp` также проверяется вручную через настоящий Clang: `sum` → `O(n)`, `printPairs` → `O(n²)`, `binarySearchLike` → `O(log n)`.

## План защиты

- **Проблема:** подсчёт циклов регулярными выражениями ломается на форматировании и вложенных конструкциях.
- **Подход:** Clang разбирает исходник в AST; небольшой обход дерева находит объявления функций и циклы.
- **Оценка:** MVP сопоставляет переменную цикла с её границей и шагом; неподдерживаемые шаблоны помечает как `O(?)`.
- **Визуализация:** таблица связывает оценку с функцией и строками, а canvas показывает форму типовых кривых роста.
- **Граница метода:** статический анализ использует упрощённые правила, не знает точную связь всех аргументов с размером входа и не моделирует библиотечные вызовы. Для сложных рекуррентных соотношений выводится `O(?)`.
